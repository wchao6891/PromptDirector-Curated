# 本机精选审核台

审核台用于维护者独立检查案例并发布到精选网站，无需 AI 参与。案例文件先保存在本机，只有点击并确认“公开发布”后才上传到 GitHub。

## 首次打开

需要 Node.js 22 或更新版本、Git、GitHub CLI（`gh`）、FFmpeg（含 `ffprobe`）和 WebP 工具（`cwebp`）。这些工具用于本地读包、验证原始媒体、生成网站缩略图和使用你的 GitHub 身份发布。

macOS 双击仓库根目录的 **打开精选审核台.command**。Windows 双击 **打开精选审核台.cmd**。终端窗口保持打开，浏览器会自动打开本机审核台。程序只监听 `127.0.0.1`，不是对外开放的管理网站。

首次发布前，在终端执行 `gh auth login`，按提示在浏览器登录拥有精选仓库写入权限的 GitHub 账号。无需把令牌交给 AI 或填进网页。审核台左下角显示依赖、登录状态和数据目录。

也可以运行 `node tools/review-desk/server.mjs --data-dir <你选择的审核数据目录>`。默认使用系统应用数据目录下的 `PromptDirector-Review`，保留上传文件、审核选择、预览和发布回执，关闭后可以继续。

## 自己的包：快捷发布

选择普通导出 ZIP，保持“我的包，导入后全选”。系统默认收录全部案例，使用文件名作为合集标题、当前 GitHub 账号作为发布署名，并自动准备简介、来源说明和首个所选案例的封面。网络来源默认保持“授权未核验”，不会因为上传者是维护者就自动认定原创。

检查标题后，点击 **发布全部 N 个案例**。这一明确操作确认公开所选原始媒体与提示词；系统自动检查、生成预览、上传并更新网站，无需重复勾选或二次点击。失败会停止后续阶段并显示原因。发布按钮前可选择“仅生成预览”查看效果，也可展开“修改署名、简介与发布设置”。

“全选所有案例”覆盖包中全部页面，不受搜索筛选影响；“选中本页”只作用于当前页。已有审核记录保留原选择与手工信息，不会重新全选。原作者可留空，已有署名仍保留。封面默认使用首个所选案例，可在案例详情更换。审核进度自动保存。

## 别人的包：下载并审核

在“审核别人投稿”粘贴当前精选仓库的 GitHub Issue 链接，点击 **下载并查看**。审核台会读取正文内的官方附件链接，把 ZIP 或全部分卷下载到本机数据目录，重组、校验后显示图片、视频和完整提示词。不是只读取投稿摘要，也不会自动上架。

别人的 Issue 投稿默认不勾选；浏览后选择收录，或点击“全选所有案例”，再点击发布。也可选择已下载的本地 ZIP，并取消“我的包，导入后全选”。关闭审核台后，下载文件与审核记录仍保留；重新打开左侧记录可继续，无需重新下载。当前不会自动扫描新投稿，也不读取评论中的追加附件。

普通导出包只提取公开案例信息；私人项目、标签、笔记、聊天、分析记录及附带脚本不会进入发布包，也不会执行。网站预览默认最长边 1200 像素，可在折叠设置中调整；下载包始终保留原始媒体。当前每个案例需包含一个图片主体，或一个视频主体及封面。

## 大包规则

- GitHub Issue 的 ZIP 附件上限为 25 MB，因此插件生成约 24 MiB 的分卷。这是传输切分，未压低媒体质量。
- 审核端的总包容量为小于 2 GiB，与 GitHub Release 单文件上限一致；可接收的分卷数按包容量、分卷容量及封装开销计算，不另设“最多六卷”。
- 自己发布时，使用普通导出 ZIP → 本机审核台 → Release，即可避免几十个 Issue 附件。若整包达到 2 GiB，应按合集拆成多个独立包，每个包仍保留原文件。
- 扩大的是整个案例包容量，媒体格式、像素和公开字段检查仍按 `submission-policy.json` 执行。单媒体无需受独立的小容量限制，但必须能完整放入案例包；不能将检查失败当作审核通过。
- 目前接受使用媒体描述结构的案例包版本 3、4、5，验证同一套公开字段与媒体关系；不通过简单改版本号转换内容。

官方依据：[Issue 附件限制](https://docs.github.com/en/get-started/writing-on-github/working-with-advanced-formatting/attaching-files)、[Release 附件限制](https://docs.github.com/en/repositories/releasing-projects-on-github/about-releases)。

## 发布失败怎么办

审核台保留发布阶段及回执。上传阶段失败时可能留下草稿 Release；文件发布成功但目录或 Pages 失败时，网站可能尚未收录。再次生成相同选择的预览并重试，会核对已上传文件的摘要；不会覆盖不同内容的同名附件。若目录被他人更新，推送会明确失败，重试会从最新目录重新准备，不覆盖别人的修改。

只有线上目录的案例数量、包摘要与预览均符合本次审核结果，才显示“发布成功”。GitHub Issue 的评论和状态不会自动改动，避免把文件已上传误当作整条审核流程完成。

网站更新通过独立的本机发布副本完成，不改动你的开发工作区。新合集使用内容确定的独立发布编号；当前工具负责新增合集，不提供替换既有合集或下架按钮。

## 维护者的审核责任

自动预检证明包的结构、媒体格式与摘要可用，不代表内容质量合格或获得原作者授权。逐案例内容判断和权利状态由你决定；第三方推荐会明确显示“授权未核验”。原始文件公开前也应检查图像中可见的信息和文件元数据。
